# 소설 분석 실행

## 언제 무엇을 쓰는가

| 상황 | 방식 | 이유 |
| --- | --- | --- |
| 처음 훑어볼 때, LLM 없이 | **빠른 분석**(규칙) | 즉시 끝나고 Ollama가 필요 없다 |
| 인물·사건 recall이 중요할 때 | **상세 분석**(Ollama 장면 map-reduce) | 길이 제한 없이 청크 단위로 추출한다 |
| 이미 분석한 원문 | 캐시 자동 사용 | 같은 원문·모델·모드는 `cache/`에서 즉시 반환 |
| 프롬프트·모델을 바꾼 뒤 | **상세 분석 새로 실행**(`force`) | 캐시 키에 프롬프트 버전이 들어가지만, 확실히 하려면 force |

빠른 분석은 항상 동작한다. 상세 분석은 선택 채널이며, 실패해도 앱은 규칙 분석으로
완전히 동작해야 한다. **상세 분석 실패를 전체 실패로 보고하지 말 것.**

## 입력

| 입력 | 방법 | 비고 |
| --- | --- | --- |
| TXT | **파일 열기** | 균등 분할 Scene |
| EPUB | **파일 열기** | `dc:title`·`dc:rights`를 읽고 **실제 챕터 경계를 Scene으로** 쓴다 |
| 위키문헌 | **위키문헌** 버튼 | 위키문헌 호스트만 허용. 권리는 `unverified`로 들어오므로 사용자가 확인해야 한다 |
| 직접 입력 | textarea 편집 후 **원문 분석** | EPUB을 편집하면 챕터 offset이 무효가 되어 균등 분할로 돌아간다 |

## 절차

1. 서버를 띄운다: `npm.cmd start` (Windows PowerShell에서 `npm`이 막히면 `npm.cmd`).
2. 상세 분석을 쓸 거면 먼저 진단한다: `GET /api/ollama/health`.
   - `reachable: false` → Ollama 미기동. 빠른 분석으로 진행하고 그 사실을 말한다.
   - 허용 모델 없음 → 4B~7B completion 모델이 필요하다. 임의로 큰 모델을 쓰지 않는다.
3. 분석을 실행한다.
   - 화면: 분석 방식 선택 → **원문 분석**
   - API: `POST /api/analyze/ollama` (`{text, model, force}`)
4. 진단(`diagnostics`)을 읽고 해석해 보고한다. 아래 표를 그대로 쓴다.

## 진단 해석

| 필드 | 정상 | 이상하면 |
| --- | --- | --- |
| `scenes_total` | 원문 길이 ÷ 약 1,000자 | 1이면 원문이 짧거나 분할이 안 된 것 |
| `scenes_failed` | 빈 배열 | 항목이 있으면 그 청크는 규칙 분석만 반영됐다. 개수를 보고한다 |
| `cache` | `hit`/`miss` | 바꿨는데 `hit`이면 force로 다시 실행 |
| `prompt_version` | `scene-v2` | 캐시 키에 들어간다. 프롬프트를 고쳤으면 올려야 한다 |
| `counts.characters` | 1 이상 | 0이면 seed 생성 실패 → 규칙 분석으로 재실행된다 |
| `audit.error` | 적을수록 좋음 | 많으면 `novel-review`로 넘긴다 |

## 하지 말 것

- 추출 결과를 확정 사실로 보고하지 않는다. 모든 항목은 `suggested` 상태로 들어오며
  검수를 거쳐야 한다. 신뢰도와 근거를 함께 제시한다.
- 원문에 없는 인물·사건을 보충하지 않는다. 작품에 대한 사전 지식으로 결과를
  "고쳐" 쓰지 않는다. 누락은 누락으로 보고한다.
- 4B~7B 밖의 모델을 쓰지 않는다. 서버가 거부한다.
- 저작권이 살아 있는 텍스트를 라이브러리에 넣지 않는다.
